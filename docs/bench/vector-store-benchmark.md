# 向量通道基准：进程内暴力检索 vs Qdrant HNSW

由 `VectorStoreBenchmarkTest` 生成（`-Dbench.enabled=true`）。

- 向量维度 256，查询数 100，语料规模 [10000, 100000]
- 语料为合成向量（簇结构 + 噪声）+ 等长合成片段，四种跑法吃同一份数据
- recall 以进程内暴力检索的 top-k 结果为精确基准
- 运行环境：Windows 11 20 核 / Java 25.0.3 / 最大堆 3072 MB / Qdrant 1.19（本机）
- 「建索引」= 从一堆片段建成整座索引（内存实现是编译倒排，Qdrant 是编译倒排 + 分批灌点），走的是生产启动时的全量重建路径

| 语料片段 | 向量通道 | 建索引 | p50 | p95 | recall@10 |
|---|---|---|---|---|---|
| 10000 | 进程内暴力（向量） | 568 ms | 3.07 ms | 4.29 ms | 1.000（基准） |
| 10000 | 进程内暴力 + BM25 融合 | 568 ms | 21.38 ms | 26.20 ms | 1.000（基准） |
| 10000 | Qdrant HNSW（向量） | 1642 ms | 3.71 ms | 6.96 ms | 1.000 |

## 内存（JVM 堆，GC 后实测增量）

- 10000 片段 · 关键词 + 元信息（堆） = 40.7 MB
- 10000 片段 · 再加向量（堆） = 50.4 MB
- 10000 片段 · 切向量库可省下 = 9.6 MB
- 100000 片段 · 关键词 + 元信息（堆） = 404.3 MB
- 100000 片段 · 再加向量（堆） = 503.6 MB
- 100000 片段 · 切向量库可省下 = 99.2 MB

## 增量写入（生产上传路径，非批量）

- 10000 片段 · 追加 1 份文档（10 片段，走关键词通道全量重编译） = 56.2 ms
- 100000 片段 · 追加 1 份文档（10 片段，走关键词通道全量重编译） = 396.5 ms

关键词通道是 copy-on-write：每写一份文档都整体重编译一次 BM25 倒排，所以单次写入成本随语料规模线性增长。真实语料只有几百个片段时这份开销可以忽略，但批量入库（十万级）必须走全量重建路径；要让增量写入也变成 O(新增) 需要给倒排加增量合并，属于后续优化项。
